# Modules — PM Sync Engine

The portable Power Map sync engine (`clearinghouse-sync-powermap`, Layer-1-adjacent:
zero usa-wa imports) and the generated PM client. Split out of
[MODULES-FRAMEWORK.md](MODULES-FRAMEWORK.md) at CR #196 so each stays loadable on its
own; the Layer-1/2 primitives these build on remain there. The deployment that *drives*
this engine is in [MODULES-SYNC.md](MODULES-SYNC.md) (the sidecar daemon) and
[MODULES-SYNC-PRODUCERS.md](MODULES-SYNC-PRODUCERS.md) (the one-shot producer CLIs).

```
packages/
  clearinghouse-sync-powermap/        — Layer 1-adjacent: portable Power Map sync engine (sibling-reusable)
    src/clearinghouse_sync_powermap/
      descriptors.py  — EntityDescriptor contract (per-entity sync behaviour; zero usa-wa imports). `_anchor_match` is the shared tolerant anchor lookup (#86): every anchor-keyed concrete `local_match` (person/org/role/assignment) delegates to it, so a pre-index duplicate anchor logs `anchor_invariant_violation` + returns a deterministic winner (newest `updated_at`, id tiebreak) instead of raising `MultipleResultsFound` and poisoning the apply path (the read-side defense in depth behind the DB unique index). Also the **LWW no-op gate** contract (#109): `local_newer_noop_gate` (opt-in flag) + the pure `observation_matches_record` (what a descriptor overrides) + the `local_newer_is_noop` template that binds them — see [`docs/LWW-NOOP-GATE.md`](../docs/LWW-NOOP-GATE.md)
      engine/         — **the portable sync engine, a package since #181 (AR-4)**. Was one 2318-line `engine.py` — `SyncEngine` alone spanning 50 methods over eight responsibilities, and the repo's #1 churn hotspot (32 of the last 300 commits). Now a thin façade over three managers on an immutable context, a **pure extraction** (no logic change, both characterisation suites pass unchanged). The seam is the **dependency direction**, not the responsibility list: a strict DAG `context ← anchors ← write ← read ← __init__`, every arrow forced by a real call. `anchors` sits *below* both paths rather than beside them because both stamp anchors (the drain on every delivery, the sweep on a PM-first adopt); `read → write` because the read path is what *discovers* a write is owed (`apply_record`'s local-newer UPDATE, the cohort's drift ENRICH) and never the reverse. Two deliberate departures from the issue's sketch, both to keep the DAG acyclic: the **dead-anchor heal lives in `read.py`, not `anchors.py`** (both its triggers are read-path events — a `deleted` feed item, a cohort re-fetch 404 — and its body calls `apply_record`, so filing it under anchors would add `anchors → read` on top of the unavoidable `read → anchors`), and the **PM read pause-and-resume lives on the context, not on the Reconciler** (the sweep, a *write* trigger, uses it too — leaving it on `read` would make write and read mutually dependent). Shared state is **constructor-injected**, never the façade passing itself (that is the god object under a new name): the `AsyncSession` is still an explicit per-call argument, nothing mutable is shared, and each warn-once throttle/counter has exactly one owner — `_warned_stuck` + `DrainStats` → the writer, `_warned_nonconverging` → the anchor manager, `_warned_dead_anchors` + the conditional-GET tallies → the reconciler. Consequently the two anchor ledgers return a `bool` instead of mutating the drain's tally object, and the writer counts its own drain.
        __init__.py   — the `SyncEngine` façade: every public method delegates to one manager, and every name the pre-split module published is re-exported (`APPLY_*`, `CHANGES_STREAM`/`REPLAY_STREAM`, `MAX_RECONCILE_PAGES`, `DrainStats`, `ReplayResult`, `OutboxBacklog`, `TRANSIENT_EXCEPTIONS`, `enrich_fingerprint`, `outbox_backlog`, `rejected_breakdown`, `nonconverging_count`, the `DEFAULT_*` tunables, and `_replay_floor`), so `from clearinghouse_sync_powermap.engine import X` and all 8 downstream call sites are unchanged. Holds no sync state of its own — it cannot drift back into a god class. A caller needing a subsystem directly reaches it via `engine.anchors` / `engine.writer` / `engine.reader` rather than widening the façade.
        context.py    — `EngineContext`, the acyclic floor: the descriptor registry + `drain_priority`, the `PowerMapClient`, every tunable and its `DEFAULT_*`, `TRANSIENT_EXCEPTIONS` / `READ_BACKOFF_SECONDS`, the PM **read** pause-and-resume (`read_with_retry` + the reconcile/conditional/backfill wrappers, usa-wa#85/#89), and `enrich_fingerprint` — the content hash three separate ledgers key on (the outbox `payload_hash`, `EnrichFingerprint`, `NonConvergenceState`), which is why it must sit below all of them. Constructor-argument validation lives here so the invariants travel with the values they constrain; `SyncEngine(...)` still raises the same `ValueError`s because it builds the context eagerly.
        anchors.py    — `AnchorManager` + the standing `nonconverging_count`. **Write side of the anchor invariant (#86)**: `anchor_taken` pre-checks for a *different* local row already holding a PM id before stamping (autoflush makes a same-drain sibling visible), consulted at **both** anchor-stamp sites — the drain delivery and the sweep's PM-first adoption (which declines the adopt and falls through to a CREATE so the drain owns the single park) — rather than stamping a duplicate whose flush would abort the whole tick and spin the cycle (the fast-loop counterpart of the #84 slow reconcile loop). An `anchor_invariant_violation` ERROR is logged once at the park (the sweep re-check passes `log=False`); the partial unique index is the hard backstop the single-drainer check can't race. **`stamp_anchor` is the single clock-preserving stamp site (#109)** — the systemic re-arm of the LWW no-op loop was the delivery itself: `set_anchor` is a plain attribute write, so the flush persisting it pushed `updated_at` to `now()` and every created row landed ahead of PM's own creation clock by the POST round-trip (the chronic org row sat 228ms ahead for 11 days on nothing else). Preserving the row's clock across the stamp lands a new row *older* than PM, so the next reconcile adopts PM's clock → parity. That preserve needs `set_last_updated`'s `flag_modified`: `updated_at` has an `onupdate` SQLAlchemy applies whenever the SET clause omits the column, and re-assigning the *same* value registers no net change — so the no-change write would silently be overwritten with `now()` (a regression guard must **flush** before asserting; the value is correct in-memory either way). `adopt_remote_clock` is the mirror-side half (skip at parity, CR-1). Also the two ledgers: **`record_reanchor`** (#108 — an in-place anchor overwrite orphans a PM id, so warn + write `AnchorReanchor` *before* the stamp destroys the old id) and **`track_convergence`** (#112 — the per-row consecutive-identical-`auto-attached` counter over `NonConvergenceState`, accruing only on a *stable re-observe*, re-arming on a changed `payload_hash`, WARNING once per row then INFO). Both return a `bool` the writer tallies. #117 Phase B lands here.
        write.py      — `OutboxWriter` + the engine-free `outbox_backlog` / `rejected_breakdown` operator surfaces. The four enqueue triggers (sweep CREATE, enrich-on-match, the LWW UPDATE, the cohort drift ENRICH), one ledger, one drainer. **Drain ordering is topological first, `next_attempt_at` second, `id` last (#96)**: `_due_entries` sorts by `drain_priority` (each entity type's index in the dependency-first `build_descriptors` registry order — that order is load-bearing here, not informational), so a dependency **root** (org/role) always drains before its dependents (assignments) inside one `LIMIT batch_limit` cut. Without it a bulk produce starves frozen roots — the role roots failed once (`next_attempt_at` fixed at ~T0), and thousands of dependency-blocked assignments re-deferring to *just before* T0 filled every batch cut ahead of them, so the roots the whole assignment tier gates on went un-attempted for ~42 min. An anchor conflict dead-letters to **UNAVAILABLE** (`_park_blocked`): a *blocking* status so the row isn't re-swept/re-POSTed and REJECTED entries don't pile up cycle-over-cycle (which would trip the #85 rejection-rise email every cycle) — a permanent "operator dedup then redrive" state, not a data edit the sweep auto-retries. **Rejected-UPDATE replay guard (#132)**: `_reject` stamps the refused payload's hash onto a CREATE/UPDATE entry (`payload_hash`; ENRICH keeps its enqueue-time #34 hash), and the read path's local-newer branch consults `rejected_identical_update` before enqueuing — when the row's latest entry is a REJECTED UPDATE whose refused hash equals the current observation hash, the re-enqueue is skipped, so a persistent 422 (e.g. PM's `chk_no_org_cycle`, #131) no longer mints a fresh REJECTED entry every reconcile (unbounded pile + the #85 rise email firing each cycle). Any payload change (the data fix) re-arms — REJECTED stays fix-triggered-retry, and the skip is deliberately NOT a clock adopt (the pending change is real and re-sends on the fix, unlike the no-op gate's spurious-skew case). Suppression stays operator-visible: `update_reject_replay_suppressed` WARNING once per row per process, `update_reject_replay_still_suppressed` INFO thereafter (the #112 throttle shape, re-armed when the guard stands down); a pre-#132 REJECTED entry (NULL hash) can't prove identity and stands down, as do unready dependencies (the #102 CR `dependencies_ready` hoist — the build dereferences dependency anchors). The **sweep** is filed here rather than under `read` despite reading from PM: its product is an outbox entry, it shares the re-enqueue blocking-status guard with every other trigger, and its PM read serves that enqueue decision rather than mirroring PM state into the cache.
        read.py       — `Reconciler`: `apply_record` (the single LWW arbiter every read converges on), the two reconcile backstops, the dead-anchor heal, the changes feed, the trailing replay, and the conditional-GET cache. **Merge-orphan anchor self-heal (#36) + `merged_into` generic re-resolution (#37)** — both triggers route here. **Local-newer no-op gate (#102/#104/#109 — the named pattern, see [`docs/LWW-NOOP-GATE.md`](../docs/LWW-NOOP-GATE.md); read it before adding a `write_enabled` producer descriptor)**: `apply_record`'s local-newer branch (keep-local → enqueue an UPDATE to push our version up) consults `descriptor.local_newer_is_noop(session, existing, record)` first — when re-producing the row wouldn't change PM it **adopts PM's clock** instead of enqueuing an identical observation, killing the LWW ping-pong at the source. Root cause: a local write that bumps `updated_at` ahead of PM without preserving the remote clock (the #65 lesson, re-armed per cohort); PM then no-ops the identical re-send **without advancing its own clock**, so the skew never resolves and the re-send repeats forever (the delivery-side re-arm and its fix are in `anchors.py`). Precondition = `anchored_cohort` ∧ `write_enabled` ∧ no gate; the audit is empirical (flat daily outbox volume + ~100% day-over-day `local_id` overlap = pure re-send). Gated cohorts: **assignment** (#102, `is_current`/`start_date`/`end_date`), **person** (#104, `legal` name vs PM's `display_name` + every #69 `additional_identifiers` entry vs PM's `identifiers[]`), **role** (#109, the match key itself — seat tuple `(org, role_type, jurisdiction, qualifier)`, or `(org, title)` + `role_type` classifier). **Organization is deliberately ungated** (#109 audit: 2 writes/day, one chronic row) — a wide five-surface comparator risks a false no-op, and a false no-op **erases** the pending change (clock adopted) rather than deferring it. Opt-in via `local_newer_noop_gate` + a pure `observation_matches_record`; `local_newer_is_noop` itself is the base **template** (flag short-circuit → `dependencies_ready` guard → build → compare), so the deps guard #102's CR added is structural, not per-descriptor. An `anchored_cohort` gate self-converges on its first post-deploy reconcile — a heal CLI is only warranted for a large pre-existing backlog (#102's ~4,300 rows got `heal_assignment_clocks`; #104's ~434 and #109's 305 did not). **Changes-feed replay backstop (#159)**: `replay_from_floor` is the trailing re-read that is replacing the O(cohort) anchored scan as the *primary* dropped-event backstop — PM's feed is monotonic but **at-least-once, not gapless** (power-map#387: a concurrent-commit skip, a lower seq committing after the live consumer advanced past it, is never re-delivered incrementally). **The floor advances as the window converges (#211)**: `REPLAY_STREAM.cursor` is the **verified watermark** — the seq the last completed pass caught up to, persisted at pass end (monotonic via `max(after, verified)` so an empty tail page never regresses it) and read back by `_replay_floor` to floor the next pass at `verified − replay_retain` (`DEFAULT_REPLAY_RETAIN` 1_000 seq — a trail sized against PM's worst-case in-flight-write span, the only thing a re-read can still recover); only a stream with no watermark bootstraps once from `high_water − replay_margin` (`DEFAULT_REPLAY_MARGIN` 10_000 seq). Safety: every seq is first replay-read by the pass that catches up past it, then re-read while inside the trail; a commit straggling more than `retain` seqs behind its assignment is the anchored scan's residual. Before #211 the floor was pinned at `high_water − margin` and the same ~10k window re-read hourly forever — 117,932 requests/19h at the rate-limit ceiling, ending in a PM 503 (and #160's 304s didn't help: 74% hit rate, still 1.97 req/s, because a 304 spends a rate-limit token — the fix had to shrink *enumeration*, not per-fetch cost). Each pass is also **budget-capped** (#211): at `replay_max_items` (`DEFAULT_REPLAY_MAX_ITEMS` 2_000) enumerated items it stops (`powermap_replay_budget_exhausted`) and the watermark carries the remainder to the next pass losslessly — so the margin bootstrap, a re-enable after a hold, or a PM bulk event becomes a series of bounded passes, never one saturated crawl; the persisted watermark equally re-costs a restart (no full re-crawl). Every item re-applies through the shared `_apply_feed_page` (extracted from `process_feed` so live + replay can't diverge; idempotent under LWW), returning a `ReplayResult(applied, healed, fell_off, floor, high_water, items, budget_exhausted)` — `healed` (INSERTED/UPDATED) is the would-heal delta the Phase-A shadow measures, `items` the request-budget observable (each item ≤ one detail GET, 304s/404s included). Never advances the live cursor; stamps its own `REPLAY_STREAM` (`changes_replay`) for cadence — which the sidecar then **end-stamps** (see `MODULES-SYNC.md`). A never-consumed feed (`high_water == 0`: fresh/empty deploy) is **skipped** (`powermap_replay_skipped_unbootstrapped`) — there's no consumed-then-skipped history to recover and reading from floor 0 would both re-read the whole retained window and spuriously trip fall-off (#159 CR-1). **Horizon fall-off**: if the floor sits below PM's oldest-retained `meta.min_seq` (power-map#388, surfaced on `ChangePage.min_seq` via `additional_properties`), the pruned `[floor, min_seq)` slice can't be replayed → `fell_off=True` → the sidecar forces the anchored scan due next cycle (the residual cover) + alerts. **Conditional GET on the reconcile (#160)**: the anchored-cohort reconcile (soon the weekly residual scan) sends PM's stored ETag as `If-None-Match` (`fetch_record_conditional` → `get_entity_conditional`, injected via the generated client's `with_headers`) and **short-circuits on a `304`** — no body, no `apply_record`, no PM→local mirror — so an unchanged row costs a cheap `304` not a full-body re-fetch (power-map#385/#292). PM's detail ETag covers child tables incl. events (the touch-cascade), so a detail `304` means the *whole* row is unchanged; only `detail_etag` is stored (`ConditionalGetState`). A stale/absent ETag only ever costs a `200` we re-apply (idempotent), never a missed update; a `404` still routes to the heal path. **The 304 still runs the local carry-payload drift backstop** (`maybe_enqueue_enrich_drift_only`, #160 CR): the reconcile's `check_drift` enrich is a **local→PM** signal (a newly-added carry field reaching the cohort — #124 parent/#69 identifiers/#31 contact), and a cohort-wide rollout is exactly when PM 304s every row, so skipping it there would silently strand the rollout; the 304 fast-path skips the PM→local apply but not the local drift enqueue (the PM-read `identifier_missing` trigger can't change without a `200`). Cuts bandwidth/DB/CPU, **not** request count (a 304 is still one round-trip + rate-limit token). `conditional_get_enabled` kill switch; `(skipped, fetched)` tally on the cycle summary. **The #160 residual extends the same store + kill switch to the replay fetch path**: `_apply_feed_page` takes a `conditional` flag and **only `replay_from_floor` passes it**. That split is the decision, not an oversight — replay re-reads a trailing window of items it has *already* applied (where the stored validator still matches → a 304), while a live feed item *means* PM changed the entity, so a conditional read there is a guaranteed `200` bought with two extra local queries per item (the anchor lookup that keys the local-id store, plus the ETag load). The live feed is left byte-identical, which also keeps the residual's risk off the primary read path. Store keys on the **local** id, so replay resolves the anchored row before the read (no anchor yet ⇒ unconditional, then the validator is stored after the insert via a post-apply re-resolve). Delete/merge/heal branches still run *before* the fetch, and a conditional `404` skips the item exactly as the unconditional one did. Nothing is stranded by the 304 short-circuit here — unlike the reconcile, the feed path has no re-enrich (that lives on the reconcile backstop alone); it forgoes only `apply_record`'s local-newer write-back re-trigger for a row edited locally between two replay passes, which the producers enqueue directly anyway. **The `304` must not strand a local-only change (#247)** — the counterpart defect to the no-op gate, and the more dangerous one because its signature is silence: the anchored-cohort reconcile is the *only* path that pushes a change on an already-anchored row (the sweep takes NULL anchors, the feed carries PM's changes), and the `304` short-circuits it before `apply_record`, so once the ETag cache warmed to full coverage the whole push half stopped with zero pending / zero rejected / zero non-converging (397 corrected assignment spans sat six clean cycles). `ConditionalGetState.row_updated_at` stamps the local row's clock beside the validator and `_local_advanced` withholds the validator when the row's clock has passed it — the row's own clock read twice, never compared against PM's (that would let a PM server running seconds ahead force a full fetch on every row forever, undoing #160 in the other direction). Self-limiting: the forced fetch re-stamps, so one full GET per local change; a NULL watermark reads as advanced (verify, don't trust), costing the cohort one pass once. `local_newer_forced` on the cycle summary is the observable — a spike after a backfill is healthy, **the same number every cycle means the push is wedged**. The replay path is deliberately exempt: it re-reads what PM's feed says changed, and a local-only edit never enters that feed
      client.py       — PowerMapClient Protocol + value types (ObservationResult, ChangePage…)
      models.py       — sync-schema OutboxEntry + SyncState + EnrichFingerprint + AnchorReanchor + **NonConvergenceState** (delivery ledger + feed cursor + enrich re-propagation stamp + orphaned-anchor ledger #108 + **non-convergence counter** #112). `NonConvergenceState` is the per-row (`(entity_type, local_id)`, twin of `EnrichFingerprint`) consecutive-identical-`auto-attached`-re-send counter (#112): a row PM keeps matching without applying our diff (the #110 classifier churn) re-sends an identical observation every reconcile cycle, and since each reconcile mints a fresh DELIVERED `OutboxEntry` the counter can't live on the entry. `_deliver`→`_track_convergence` bumps `count` on a stable re-observe (`auto-attached` ∧ `pm_id`==existing anchor ∧ unchanged `payload_hash`), resets it on a genuine change (first attach / re-anchor #108 / `new` / changed payload = the re-arm); past `nonconvergence_threshold` the row is flagged (`DrainStats.non_converging` + the `nonconverging_count` standing query the cycle summary alerts on). The per-row log is **throttled** like `_warned_stuck`: `observation_not_converging` WARNING once per row per process, `observation_still_not_converging` INFO on every drain thereafter (a flagged row re-flags by definition — a #110-sized 305-row cohort would otherwise emit 305 WARNINGs per drain). The throttle **re-arms** when the counter resets, so a second episode after a fix WARNs again rather than the rise-email pointing at a stale line. Detection-only (Phase A) — no park, so no false-park risk; the re-POST cost is already bounded by the #85 PM min-interval + 12h reconcile cadence. `AnchorReanchor` is the append-only record of every in-place `pm_*_id` overwrite: when a delivery resolves to a *different* PM id than the row's existing anchor (PM dedups assignments on `(person, role, start_date)`, so a start-date correction mints a fresh assignment and orphans the old one), `_deliver` writes one row *before* the stamp destroys the old id — the only durable, queryable handle on the orphaned upstream assignment the #311 cleanup will reconcile (journald is not retained). Paired with a WARNING `anchor_reanchored`; keyed for scan on `old_pm_id`. **`ConditionalGetState`** (#160) is the per-row (`(entity_type, local_id)`, twin of `EnrichFingerprint`) PM `detail_etag` store the reconcile sends as `If-None-Match` to earn a `304` instead of a full re-fetch (power-map#385); only the detail ETag (it covers child tables incl. events via the touch-cascade), nullable (never-fetched → unconditional next pass). Carries `row_updated_at` since #247 — the **local** row's clock as of that fetch, the purely-local signal that a change is waiting to go up (see the `read.py` entry and [`docs/LWW-NOOP-GATE.md`](../docs/LWW-NOOP-GATE.md) § The inverse)
      testing.py      — shipped test doubles (FakeEntity/Descriptor/Client) for this + sibling tests
      pmclient.py     — GeneratedPowerMapClient: adapts the generated SDK to the PowerMapClient Protocol
```

## Regenerating the PM client

`packages/powermap-client/` is generated from Power Map's live OpenAPI; never hand-edit it. To refresh after PM ships API changes:

```bash
cd /tmp && rm -rf pmgen && mkdir pmgen && cd pmgen
curl -fsS https://power-map.exe.xyz/openapi.json -o pm-openapi.json
printf 'package_name_override: powermap_client\nproject_name_override: powermap-client\n' > cfg.yml
uvx openapi-python-client generate --path pm-openapi.json --config cfg.yml --meta uv
# review the diff, then replace the vendored copy:
rm -rf /home/exedev/usa-wa/packages/powermap-client
cp -r powermap-client /home/exedev/usa-wa/packages/powermap-client
```

Then `uv sync` and re-run the `GeneratedPowerMapClient` wrapper tests — the wrapper's path/model dispatch (`pmclient.py`) is what breaks if PM renames an operation or model.
