model), the portable Power Map sync engine, and the generated PM client. The
reusable Layer-3 pattern these support is in [ARCHITECTURE.md](ARCHITECTURE.md).

Was one 2318-line `engine.py` — `SyncEngine` alone spanning 50 methods over eight responsibilities, and the repo's #1 churn hotspot (32 of the last 300 commits). Now a thin façade over three managers on an immutable context, a **pure extraction** (no logic change, both characterisation suites pass unchanged). The seam is the **dependency direction**, not the responsibility list: a strict DAG `context ← anchors ← write ← read ← __init__`, every arrow forced by a real call. `anchors` sits *below* both paths rather than beside them because both stamp anchors (the drain on every delivery, the sweep on a PM-first adopt); `read → write` because the read path is what *discovers* a write is owed (`apply_record`'s local-newer UPDATE, the cohort's drift ENRICH) and never the reverse. Shared state is **constructor-injected**, never the façade passing itself (that is the god object under a new name): the `AsyncSession` is still an explicit per-call argument, nothing mutable is shared, and each warn-once throttle/counter has exactly one owner — `_warned_stuck` + `DrainStats` → the writer, `_warned_nonconverging` → the anchor manager, `_warned_dead_anchors` + the conditional-GET tallies → the reconciler. Preserving the row's clock across the stamp lands a new row *older* than PM, so the next reconcile adopts PM's clock → parity. That preserve needs `set_last_updated`'s `flag_modified`: `updated_at` has an `onupdate` SQLAlchemy applies whenever the SET clause omits the column, and re-assigning the *same* value registers no net change — so the no-change write would silently be overwritten with `now()` (a regression guard must **flush** before asserting; the value is correct in-memory either way). `adopt_remote_clock` is the mirror-side half (skip at parity, CR-1). Also the two ledgers: **`record_reanchor`** (#108 — an in-place anchor overwrite orphans a PM id, so warn + write `AnchorReanchor` *before* the stamp destroys the old id) and **`track_convergence`** (#112 — the per-row consecutive-identical-`auto-attached` counter over `NonConvergenceState`, accruing only on a *stable re-observe*, re-arming on a changed `payload_hash`, WARNING once per row then INFO). Both return a `bool` the writer tallies. #117 Phase B lands here.
        write.py      — `OutboxWriter` + the engine-free `outbox_backlog` / `rejected_breakdown` operator surfaces. The four enqueue triggers (sweep CREATE, enrich-on-match, the LWW UPDATE, the cohort drift ENRICH), one ledger, one drainer. **Drain ordering is topological first, `next_attempt_at` second, `id` last (#96)**: `_due_entries` sorts by `drain_priority` (each entity type's index in the dependency-first `build_descriptors` registry order — that order is load-bearing here, not informational), so a dependency **root** (org/role) always drains before its dependents (assignments) inside one `LIMIT batch_limit` cut. Without it a bulk produce starves frozen roots — the role roots failed once (`next_attempt_at` fixed at ~T0), and thousands of dependency-blocked assignments re-deferring to *just before* T0 filled every batch cut ahead of them, so the roots the whole assignment tier gates on went un-attempted for ~42 min. An anchor conflict dead-letters to **UNAVAILABLE** (`_park_blocked`): a *blocking* status so the row isn't re-swept/re-POSTed and REJECTED entries don't pile up cycle-over-cycle (which would trip the #85 rejection-rise email every cycle) — a permanent "operator dedup then redrive" state, not a data edit the sweep auto-retries. **Rejected-UPDATE replay guard (#132)**: `_reject` stamps the refused payload's hash onto a CREATE/UPDATE entry (`payload_hash`; ENRICH keeps its enqueue-time #34 hash), and the read path's local-newer branch consults `rejected_identical_update` before enqueuing — when the row's latest entry is a REJECTED UPDATE whose refused hash equals the current observation hash, the re-enqueue is skipped, so a persistent 422 (e.g. PM's `chk_no_org_cycle`, #131) no longer mints a fresh REJECTED entry every reconcile (unbounded pile + the #85 rise email firing each cycle). Any payload change (the data fix) re-arms — REJECTED stays fix-triggered-retry, and the skip is deliberately NOT a clock adopt (the pending change is real and re-sends on the fix, unlike the no-op gate's spurious-skew case). Suppression stays operator-visible: `update_reject_replay_suppressed` WARNING once per row per process, `update_reject_replay_still_suppressed` INFO thereafter (the #112 throttle shape, re-armed when the guard stands down); a pre-#132 REJECTED entry (NULL hash) can't prove identity and stands down, as do unready dependencies (the #102 CR `dependencies_ready` hoist — the build dereferences dependency anchors). The **sweep** is filed here rather than under `read` despite reading from PM: its product is an outbox entry, it shares the re-enqueue blocking-status guard with every other trigger, and its PM read serves that enqueue decision rather than mirroring PM state into the cache.
        read.py       — `Reconciler`: `apply_record` (the single LWW arbiter every read converges on), the two reconcile backstops, the dead-anchor heal, the changes feed, the trailing replay, and the conditional-GET cache. **Merge-orphan anchor self-heal (#36) + `merged_into` generic re-resolution (#37)** — both triggers route here. **Local-newer no-op gate (#102/#104/#109 — the named pattern, see [`docs/LWW-NOOP-GATE.md`](../docs/LWW-NOOP-GATE.md); read it before adding a `write_enabled` producer descriptor)**: `apply_record`'s local-newer branch (keep-local → enqueue an UPDATE to push our version up) consults `descriptor.local_newer_is_noop(session, existing, record)` first — when re-producing the row wouldn't change PM it **adopts PM's clock** instead of enqueuing an identical observation, killing the LWW ping-pong at the source. Root cause: a local write that bumps `updated_at` ahead of PM without preserving the remote clock (the #65 lesson, re-armed per cohort); PM then no-ops the identical re-send **without advancing its own clock**, so the skew never resolves and the re-send repeats forever (the delivery-side re-arm and its fix are in `anchors.py`). Precondition = `anchored_cohort` ∧ `write_enabled` ∧ no gate; the audit is empirical (flat daily outbox volume + ~100% day-over-day `local_id` overlap = pure re-send). Gated cohorts: **assignment** (#102, `is_current`/`start_date`/`end_date`), **person** (#104, `legal` name vs PM's `display_name` + every #69 `additional_identifiers` entry vs PM's `identifiers[]`), **role** (#109, the match key itself — seat tuple `(org, role_type, jurisdiction, qualifier)`, or `(org, title)` + `role_type` classifier). **Organization is deliberately ungated** (#109 audit: 2 writes/day, one chronic row) — a wide five-surface comparator risks a false no-op, and a false no-op **erases** the pending change (clock adopted) rather than deferring it. Opt-in via `local_newer_noop_gate` + a pure `observation_matches_record`; `local_newer_is_noop` itself is the base **template** (flag short-circuit → `dependencies_ready` guard → build → compare), so the deps guard #102's CR added is structural, not per-descriptor. An `anchored_cohort` gate self-converges on its first post-deploy reconcile — a heal CLI is only warranted for a large pre-existing backlog (#102's ~4,300 rows got `heal_assignment_clocks`; #104's ~434 and #109's 305 did not). **Changes-feed replay backstop (#159)**: `replay_from_floor` is the trailing re-read that is replacing the O(cohort) anchored scan as the *primary* dropped-event backstop — PM's feed is monotonic but **at-least-once, not gapless** (power-map#387: a concurrent-commit skip, a lower seq committing after the live consumer advanced past it, is never re-delivered incrementally). It reads `high_water − replay_margin` (`_replay_floor`, `DEFAULT_REPLAY_MARGIN` 10_000 seq) from the *live* `changes_feed` cursor each pass and re-applies every item through the shared `_apply_feed_page` (extracted from `process_feed` so live + replay can't diverge; idempotent under LWW), returning a `ReplayResult(applied, healed, fell_off, floor, high_water)` — `healed` (INSERTED/UPDATED) is the would-heal delta the Phase-A shadow measures. Never advances the live cursor; stamps its own `REPLAY_STREAM` (`changes_replay`) for cadence. A never-consumed feed (`high_water == 0`: fresh/empty deploy) is **skipped** (`powermap_replay_skipped_unbootstrapped`) — there's no consumed-then-skipped history to recover and reading from floor 0 would both re-read the whole retained window and spuriously trip fall-off (#159 CR-1). **Horizon fall-off**: if the floor sits below PM's oldest-retained `meta.min_seq` (power-map#388, surfaced on `ChangePage.min_seq` via `additional_properties`), the pruned `[floor, min_seq)` slice can't be replayed → `fell_off=True` → the sidecar forces the anchored scan due next cycle (the residual cover) + alerts. **Conditional GET on the reconcile (#160)**: the anchored-cohort reconcile (soon the weekly residual scan) sends PM's stored ETag as `If-None-Match` (`fetch_record_conditional` → `get_entity_conditional`, injected via the generated client's `with_headers`) and **short-circuits on a `304`** — no body, no `apply_record`, no PM→local mirror — so an unchanged row costs a cheap `304` not a full-body re-fetch (power-map#385/#292). PM's detail ETag covers child tables incl. events (the touch-cascade), so a detail `304` means the *whole* row is unchanged; only `detail_etag` is stored (`ConditionalGetState`). A stale/absent ETag only ever costs a `200` we re-apply (idempotent), never a missed update; a `404` still routes to the heal path. **The 304 still runs the local carry-payload drift backstop** (`maybe_enqueue_enrich_drift_only`, #160 CR): the reconcile's `check_drift` enrich is a **local→PM** signal (a newly-added carry field reaching the cohort — #124 parent/#69 identifiers/#31 contact), and a cohort-wide rollout is exactly when PM 304s every row, so skipping it there would silently strand the rollout; the 304 fast-path skips the PM→local apply but not the local drift enqueue (the PM-read `identifier_missing` trigger can't change without a `200`). Cuts bandwidth/DB/CPU, **not** request count (a 304 is still one round-trip + rate-limit token). `conditional_get_enabled` kill switch; `(skipped, fetched)` tally on the cycle summary
      client.py       — PowerMapClient Protocol + value types (ObservationResult, ChangePage…)
      models.py       — sync-schema OutboxEntry + SyncState + EnrichFingerprint + AnchorReanchor + **NonConvergenceState** (delivery ledger + feed cursor + enrich re-propagation stamp + orphaned-anchor ledger #108 + **non-convergence counter** #112). `NonConvergenceState` is the per-row (`(entity_type, local_id)`, twin of `EnrichFingerprint`) consecutive-identical-`auto-attached`-re-send counter (#112): a row PM keeps matching without applying our diff (the #110 classifier churn) re-sends an identical observation every reconcile cycle, and since each reconcile mints a fresh DELIVERED `OutboxEntry` the counter can't live on the entry. `_deliver`→`_track_convergence` bumps `count` on a stable re-observe (`auto-attached` ∧ `pm_id`==existing anchor ∧ unchanged `payload_hash`), resets it on a genuine change (first attach / re-anchor #108 / `new` / changed payload = the re-arm); past `nonconvergence_threshold` the row is flagged (`DrainStats.non_converging` + the `nonconverging_count` standing query the cycle summary alerts on). The per-row log is **throttled** like `_warned_stuck`: `observation_not_converging` WARNING once per row per process, `observation_still_not_converging` INFO on every drain thereafter (a flagged row re-flags by definition — a #110-sized 305-row cohort would otherwise emit 305 WARNINGs per drain). ## Regenerating the PM client

`packages/powermap-client/` is generated from Power Map's live OpenAPI; never hand-edit it. To refresh after PM ships API changes:

```bash
cd /tmp && rm -rf pmgen && mkdir pmgen && cd pmgen
curl -fsS https://power-map.exe.xyz/openapi.json -o pm-openapi.json
printf 'package_name_override: powermap_client\nproject_name_override: powermap-client\n' > cfg.yml
uvx openapi-python-client generate --path pm-openapi.json --config cfg.yml --meta uv
# review the diff, then replace the vendored copy:
rm -rf /home/exedev/usa-wa/packages/powermap-client
cp -r powermap-client /home/exedev/usa-wa/packages/powermap-client
```

Then `uv sync` and re-run the `GeneratedPowerMapClient` wrapper tests — the wrapper's path/model dispatch (`pmclient.py`) is what breaks if PM renames an operation or model.
